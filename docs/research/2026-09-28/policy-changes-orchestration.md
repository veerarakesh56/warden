## (a) Should WARDEN's Python verifier be complemented or replaced by a policy engine?

### Takeaway
Keep the Python verifier as the only decider; do not port P1-P16 to a policy engine. Most of the rules (P8, P9, P11, P12) are judgments over evidence that has to be computed first, and Rego or Cedar would only receive booleans that Python already worked out. The two additions worth considering are a Kubernetes ValidatingAdmissionPolicy (CEL) that enforces the live write path's replica limits on the API server's side, and Checkov (plus conftest only if needed) run next to Helios on Terraform plans. Cedar is the best fit if an engine is ever added for the "principal x environment x action" part, but it is optional.

### Inferences
- **Replace: no.** P2, P5, P8, P9, P11 and P12 need evidence-derived facts (OOM counts, "every pod failing", replica lag, deploy-in-window, read failures) computed by Python in `symptoms`. Porting them means Python computes the facts and Rego/Cedar evaluates `if fact then deny`. That adds a second language, a sidecar or WASM runtime and a JSON contract, and the logic stays where it is. The replay, mutation-test and AST tests all run against Python today.
- **Complement, cheapest first:**
  1. A Kubernetes **ValidatingAdmissionPolicy** (CEL, native, no Kyverno) bound to the `warden-remediator` ServiceAccount that denies `spec.replicas < 1` or `> ceiling`. This is the "RBAC is the boundary" idea extended to values: a verifier or clamp bug still cannot scale to 0. VAP was GA in K8s 1.30 (training knowledge, not re-verified here). Skip Kyverno unless you need mutation or reports.
  2. **Checkov (Apache-2.0, pip-installable) next to Helios.** Helios proves the properties you specify (Z3), while Checkov gives 1,000+ generic misconfiguration checks for free. Helios stays the gate and Checkov is advisory breadth. **Do not add trivy-action.** If Trivy is used, pin the binary by digest and the action by commit SHA.
  3. **Cedar only if** approver/principal rules outgrow `environments.yaml` and `approvers.yaml`. Its analyzability (policy-change and conflict proofs) matches the Helios/Z3 approach better than Rego does, and it is the de-facto agent-tool-call language (AgentCore). OPA is safe from a governance standpoint (CNCF, active releases) but gives WARDEN nothing its Python does not already do.
- Permit.io is paid (Cerbos PDP or Cedar are the free alternatives). AgentCore Policy is paid, AWS-only and gateway-bound, so it is not a fit for WARDEN's free-only rule.

## (b) Best free way to build a change timeline (GitHub deploys, Terraform, ECS, EKS, Lambda)

### Takeaway
Plan section 11b is right and still the best free design: stamp the SHA everywhere, use GitHub Deployments, CloudTrail event history, EventBridge rules to a CloudWatch log group, and one `recent_changes()` reader. No free product does "which change broke prod" end to end: Cursor Rollouts, Sleuth, Datadog Bits and LinearB are all paid, and DevLake is heavy and computes DORA metrics, not incident attribution. Changes to 11b: use the ECS "Service Action" deployment events, use OTel `deployment.*` resource attributes (there is no OTel deploy event), and replace the dormant resmoio event exporter with the ownkube fork, or skip it because WARDEN already reads ReplicaSet history.

### Cited Findings
- **Cursor Rollouts** launched 2026-09-23 for Teams and Enterprise. It reads the diff before merge, writes a monitoring plan, compares post-deploy signals with a baseline, names the suspect change, and opens a revert PR or hands off to an agent. It does not merge or roll back by itself but can pause a progressive rollout. It integrates with Datadog, Grafana and Honeycomb. It came from Cursor's acquisition of Firetiger. — [Cursor blog](https://cursor.com/blog/rollouts-and-security-reviewer); [The New Stack](https://thenewstack.io/cursor-rollouts-firetiger-production/)
- **Sleuth** (deploy tracking, paid) is still operating. No acquisition or shutdown was found. — [G2](https://www.g2.com/products/sleuth/reviews); [Sleuth docs](https://help.sleuth.io/modeling-your-deployments)
- **Datadog Bits AI SRE** (paid) adds recent code changes, infrastructure events and dependencies to an alert, and attributes incidents to recent deploys through the GitHub integration. Tested across 2,000+ customer environments. — [Datadog](https://www.datadoghq.com/product/ai/bits-ai-sre/); [Help Net Security](https://www.helpnetsecurity.com/2025/12/03/datadog-bits-ai-sre-agent/)
- Traversal (an AI SRE vendor): 2026 tools mostly got faster at *correlating* signals, not at isolating cause. "correlation tells you what broke together while causation tells you why." — [Traversal 2026](https://www.traversal.com/blog/ai-in-incident-response-state-of-the-field-2026-sre)
- **Apache DevLake** is still an Incubator project ("close to graduation" per Feb 2025 board minutes). It ships DORA dashboards. — [Incubator status](https://incubator.apache.org/projects/devlake.html); [GitHub](https://github.com/apache/incubator-devlake)
- **GitHub Deployments API**: `ref`, `sha`, `environment`, `payload` (free-form JSON), `task`. Statuses: error, failure, pending, in_progress, queued, success, with a log URL. The `repo_deployment` scope gives deployment access without code access. — [GitHub REST docs](https://docs.github.com/en/rest/deployments/deployments)
- **OpenTelemetry**: `deployment.environment.name` is Stable. `deployment.id`, `deployment.name` and `deployment.status` (`failed`/`succeeded`) are in Development. **No deployment event is defined.** There are separate CI/CD semconv for pipeline spans, metrics and logs (`cicd.pipeline.*`), first in semconv v1.27.0. — [OTel deployment registry](https://opentelemetry.io/docs/specs/semconv/registry/attributes/deployment/); [OTel CI/CD spans](https://opentelemetry.io/docs/specs/semconv/cicd/cicd-spans/); [OTel CI/CD SIG blog](https://opentelemetry.io/blog/2025/otel-cicd-sig/)
- **ECS → EventBridge**: detail-type `ECS Service Action` with `SERVICE_DEPLOYMENT_IN_PROGRESS`, `SERVICE_DEPLOYMENT_COMPLETED` (covers rollback or a new revision) and `SERVICE_DEPLOYMENT_FAILED` (CloudWatch alarm or circuit breaker), plus `SERVICE_TASK_START_IMPAIRED` and placement or configuration failures with a `reason`. — [AWS ECS docs](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs_service_events.html)
- **kubernetes-event-exporter**: the resmoio repo has been dormant since JumpCloud acquired Resmo (2024). ownkube/kubernetes-events-exporter is an actively maintained fork that fixes event loss and adds a Prometheus sink and Loki auth. — [ownkube fork](https://github.com/ownkube/kubernetes-events-exporter); [resmoio](https://github.com/resmoio/kubernetes-event-exporter)
- OneUptime guide: record deploys and correlate them through `deployment.*` resource attributes on every signal. — [OneUptime](https://oneuptime.com/blog/post/2026-02-06-correlate-deployments-incidents-opentelemetry/view)

### Inferences
- Keep 11b as written, with these edits:
  - EventBridge rule pattern `{"source":["aws.ecs"],"detail-type":["ECS Service Action"],"detail":{"eventName":[{"prefix":"SERVICE_DEPLOYMENT_"}]}}`. Default-bus AWS service events are free, and the rule itself is free.
  - Emit `service.version=<sha>` and `deployment.id=<gh run id>` as OTel resource attributes. Do not invent a deploy-event schema, because OTel has none.
  - For EKS, WARDEN already reads ReplicaSet revision history, so a separate event exporter is optional (YAGNI). If one is added, use the ownkube fork (check its licence first) or Argo CD Notifications if Argo is present.
- Lambda: `UpdateFunctionCode` and `PublishVersion` are CloudTrail management events, so LookupEvents (free, 90 days) covers them without data events. This is from training knowledge; verify event names in the console.
- The "suspect, never cause" rule in 11b matches Traversal's correlation-vs-causation warning and Cursor's design (it names a suspect and a human reverts). That framing is defensible and matches the state of the art.
- Free substitute for Rollouts, Sleuth and LinearB: GitHub Deployments + SHA stamping + `recent_changes()`. Free substitute for DevLake: nothing needed until DORA metrics are wanted.

## (c) Is Temporal the right orchestrator for governed remediation?

### Takeaway
Yes, keep Temporal. It is MIT-licensed, self-hosts on Postgres, has mature signals and updates for approvals, deterministic replay for audit, and actively developed AI integrations. It also fits what WARDEN has already built (RemediationWorkflow). One must-do: self-hosted Temporal runs with **no auth by default** (noopAuthorizer), so the approval signal has to be protected with mTLS plus an Authorizer and ClaimMapper, or kept on a private network. The only serious lighter alternative is DBOS (MIT, a library on Postgres). Restate is BSL, Inngest is SSPL, and LangGraph self-hosting is enterprise-only.

**Alternatives: one paragraph each**
- **Restate**: a single Rust binary with no external database. ### Inferences
- **Stay on Temporal.** Human-in-the-loop fits as a signal or Update carrying `approve(plan_hash)`. Replay history is an audit record, and the history-replay tests are already in section 14 of the plan. The licence is MIT, and self-hosting runs on the Postgres already planned. Moving now would throw away Phase 2 work for no gain in safety.
- **Required hardening** (it is the approval channel):
  - mTLS on the frontend.
  - A JWT ClaimMapper plus an Authorizer so that only the approver identity can send `approve`, or bind the frontend to localhost or a private subnet.
  - A payload codec if redacted evidence still counts as sensitive.
  - Pin ≥ v1.31.2 for CVE-2026-5724.
  - Plan for the 1.32 visibility breaking change: strict search-attribute types.
- Principal Attribution is Cloud-only (pre-release), so self-hosted WARDEN must keep its own signed approver record, which it already plans (`approvals.py`, signed audit).
- "Exactly-once side effects" does not exist in any of these engines for external APIs: activities are at-least-once. WARDEN's digest-bound approval plus idempotent remediation (check the current replicas before patching) is the correct design whichever engine is used.
- If Temporal ever proves too heavy on the lab box, DBOS (MIT, Postgres only, no server) is the fallback. Restate and Inngest fail the free/OSI preference on licence, LangSmith Deployment is paid to self-host, and Durable Task and Step Functions are cloud-locked.
